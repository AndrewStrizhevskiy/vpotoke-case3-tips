# Информационная безопасность — кейс 3 «Онлайн-чаевые»

Заполненный шаблон `11_ИБ.md`. Строки организаторов (U-1, U-2 и первые ячейки таблиц)
оставлены без изменений. Обоснования решений — в ADR-002, 003, 008, 009.

## 1. Модель угроз

| ID | Угроза | Актив | Вероятность | Ущерб | Источник |
|-|-|-|-|-|-|
| U-1 | Подделка QR | деньги клиента | средняя | высокий | злоумышленник |
| U-2 | Повторное использование QR (replay) | деньги клиента | средняя | средний | перехват |
| U-3 | Кража реквизитов официанта | реквизиты для выплат, ПДн сотрудника | средняя | высокий | утечка БД или логов, внутренний нарушитель |
| U-4 | Двойное списание при повторе | деньги клиента | высокая (ретраи сети, двойное нажатие) | средний | сбой сети, клиентское приложение |
| U-5 | Манипуляции официанта с суммой | деньги клиента, доверие к заведению | средняя | средний | недобросовестный официант |
| U-6 | Отсутствие аудита | возможность разобрать спор | высокая, если не заложить | высокий | ошибка проектирования |
| U-7 | Перебор `qr_id` и `payment_id` | данные чеков, чужие платежи | высокая (номера идут подряд) | средний | злоумышленник |
| U-8 | Утечка HMAC-ключа | целостность всех QR | низкая | высокий | ключ в Git или в логах, взлом сервера |

U-7 и U-8 добавлены сверх шаблона. U-7 появилась после разбора ссылки `?qr={qr_id}` (ADR-003),
U-8 — потому что вся защита от U-1 держится на секрете.

## 2. Меры защиты

| ID | Угроза | Мера | Остаточный риск |
|-|-|-|-|
| U-1 | подделка QR | HMAC-SHA256 + секрет | низкий |
| U-2 | replay | nonce + TTL 24 ч | низкий |
| U-3 | кража реквизитов | хранится только маска `****NNNN`, полные реквизиты лежат у провайдера выплат; маскирование логов; RBAC: реквизиты видит только сам официант | низкий |
| U-4 | двойное списание | `idempotency_key` + атомарная запись; блокировка QR, пока платёж в CREATED или PENDING; nonce гасится на SUCCESS; отмена из PENDING запрещена; сверка закрывает зависшие PENDING | низкий |
| U-5 | манипуляции с суммой | сумма берётся из реестра кассы, а не из запроса (`AMOUNT_MISMATCH`); QR привязан к `receipt_id` (`RECEIPT_MISMATCH`); официант не может менять реестр; каждое действие в аудите | средний: доверяем кассе мерчанта |
| U-6 | отсутствие аудита | событие на каждый переход в одной транзакции с ним; журнал только дописывается (UPDATE и DELETE запрещены правами БД); `actor` и время UTC | низкий |
| U-7 | перебор id | подпись в ссылке (`sig`) и единый ответ `INVALID_QR`; `confirm_token` для операций с платежом; rate limit, 5 неверных подписей → блок на 15 мин | низкий |
| U-8 | утечка ключа | ключ только в окружении или secret manager, не в Git и не в логах; ротация с окном 24 ч | средний: при взломе сервера ключ доступен |

## 3. RBAC — матрица прав

Совпадает с матрицей в `02_roles.md`. Принципы: минимальные права и разделение обязанностей —
администратор управляет платформой, но не участвует в платежах.

| Действие | Мерчант | Официант | Клиент | Администратор |
|-|-|-|-|-|
| Регистрация | да | да, по приглашению мерчанта | нет, анонимен | нет, активирует заявки |
| Генерация QR | да | да, только на себя | нет | нет |
| Просмотр своих чаевых | да, по заведению | да, только свои | нет | да, все (разбор инцидентов) |
| Сканирование QR | нет | нет | да | нет |
| Оплата чаевых | нет | нет | да | нет |
| Просмотр отчёта | да, только своего заведения | нет, только свои чаевые | нет | да |
| Блокировка мерчанта | нет | нет | нет | да |
| Изменение справочников | да, свои сотрудники | нет | нет | да, мерчанты и статусы |

Как это проверяется: роль, `merchant_id` и `employee_id` берутся из JWT, а не из параметров запроса.
Запрос официанта с чужим `employee_id` получает 403 `ACCESS_DENIED`.
У клиента токена нет: его права подтверждают подпись QR и `confirm_token`.

## 4. Аудит — структура события

| Поле | Тип | Пример | Зачем |
|-|-|-|-|
| event_id | string | evt_0001 | уникальный ID |
| payment_id | string | p_0001 | привязка к платежу |
| qr_id | string | qr_001 | разбор всех попыток по одному чеку |
| action | enum | payment_confirmed | что произошло |
| from_status | enum / null | PENDING | статус до перехода (null при создании) |
| to_status | enum | SUCCESS | статус после перехода |
| amount_total | decimal | 668.85 | сумма на момент события, для споров о сумме |
| actor | enum | system | кто инициировал: client, system или officer |
| at | datetime | 2025-11-01T18:00:00Z | когда, всегда UTC |

Пример — событие T3-1 (qr_001, 637.00 + 31.85). `actor = officer` — администратор при ручном разборе инцидента.
В события не попадают подпись, nonce, токены и реквизиты.

## 5. Защита данных

**Что нельзя хранить**

- **PAN / CVV** — не хранятся и через платформу не проходят: карту клиент вводит на странице
  платёжного шлюза. CVV по PCI DSS хранить нельзя вообще, даже в зашифрованном виде.
- **Полные реквизиты официанта** — хранятся только у провайдера выплат. У платформы есть
  маска `****NNNN` и токен для выплаты.

**Что можно хранить**

- `payment_details` — только маска `****NNNN`.
- `signature` — да, это не секрет: она и так видна в ссылке. Без ключа подделать её нельзя.
- `nonce` — да, тоже публичен. Защищает не его секретность, а одноразовость: после SUCCESS
  по QR новый платёж невозможен (`QR_USED`).

**Персональные данные.** Имя официанта — ПДн (152-ФЗ). Клиенту на форме показывается только
«Иванов И.», полного имени платформа не хранит. Клиент анонимен; IP для rate limit хранится не дольше 24 ч.

**Маскирование логов — пример:**

До: `verify qr_001 sig=68d0f361ac38c12b nonce=c82561 card=2200123456781001`

После: `verify qr_001 sig=68d0…[masked] nonce=[masked] card=****1001`

## 6. Секреты и ключи

| Секрет | Где хранится | Кто имеет доступ | Ротация |
|-|-|-|-|
| HMAC-ключ | переменная окружения `TIPS_HMAC_SECRET`, в проде — secret manager | только процесс сервиса; запись — администратор инфраструктуры | раз в 90 дней и сразу при подозрении на утечку; 24 ч проверка принимает оба ключа (QR живёт не дольше) |
| Пароль БД | переменная окружения, в проде — secret manager | сервис; DBA — отдельной учётной записью | раз в 90 дней |
| Ключ подписи JWT | secret manager | только API | раз в 90 дней, с перекрытием на время жизни токена |

**Правила:** секреты не в Git, не логируются, только `os.environ`.

В прототипе организаторов ключ зашит в код (`SECRET = b"demo-secret-k3"`). Это нужно исправить
на `os.environ["TIPS_HMAC_SECRET"]` (ADR-009). Значение `demo-secret-k3` — демо-ключ, которым
подписаны seed-данные; в README он указан как тестовый.
