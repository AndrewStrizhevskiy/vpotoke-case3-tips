# Эксплуатация: развёртывание, резервные копии, мониторинг

Схема на одной машине: `docker-compose.yml` (база PostgreSQL 16, разовая миграция, сервис, воркер сверки). TLS, публичный адрес и
ограничения по IP даёт прокси перед сервисом (nginx, Caddy, облачный балансировщик). Образ собирается из `Dockerfile`: непривилегированный
пользователь, файловая система контейнеров только для чтения, без capabilities.

> Сборка образа и `docker compose up` в этой среде **не проверены**: демон Docker на машине разработки не запущен. Проверены сами
> сценарии (миграции, запуск сервиса, резервная копия, восстановление, проверки production, метрики). Первую сборку выполните на сервере и
> пройдите чек-лист ниже.

## 1. Первый запуск

1. `cp deploy/env.example deploy/.env`, заполнить. Ключи: `python -m tips.http.keys` (JWT) и `python -m tips.http.keys qr` (QR v2),
   `TIPS_HMAC_SECRET` случайный (`openssl rand -hex 24`), пароль базы случайный. Файл `.env` в Git не попадает.
2. `docker compose --env-file deploy/.env up -d --build`. Порядок: база → миграции (`migrate`, разово) → сервис и воркер.
3. Первый администратор (пароль из `TIPS_NEW_PASSWORD`, в аргументах и журналах его нет):
   `docker compose run --rm -e TIPS_NEW_PASSWORD=... app python -m tips.adapters.sql.admin create-user --login admin --role admin`.
4. Сервис в production не стартует при небезопасной конфигурации и пишет список причин ([prodcheck](architecture.md)).

Чек-лист после запуска: `GET /health` отвечает 200; `GET /docs` отвечает 404; ответы содержат HSTS и `Content-Security-Policy`;
`GET /metrics` без токена отвечает 404, с токеном 200; `docker compose logs app` не содержит `sig=`, токенов и номеров карт; `docker compose ps`
показывает `app` и `worker` в состоянии healthy/running.

## 2. Обновление

1. Резервная копия (раздел 3).
2. `git pull && docker compose --env-file deploy/.env up -d --build`: `migrate` применит новые миграции до запуска новых контейнеров.
   Миграции обратимы (`alembic downgrade -1`, проверено для 0005), но откат данных не заменяет копию.
3. Откат кода: вернуть прежний образ; миграции откатываются отдельно, только если новая версия их ещё не использовала.

## 3. Резервные копии и восстановление

| Что | Как |
|-|-|
| Ежедневная копия | `deploy/backup.sh /backups 14` (cron), формат custom, права 600, старше 14 дней удаляются. Копию хранить вне машины с базой |
| Восстановление | в ПУСТУЮ базу: `deploy/restore.sh файл.dump`; непустую скрипт не трогает |
| Проверка копии | `deploy/verify.sh` на восстановленной базе: версия миграций, число платежей и аудита, у каждого платежа есть запись аудита. Раз в неделю восстанавливать последнюю копию в отдельную базу и запускать проверку: непроверенная копия копией не считается |
| Потеря не более нескольких минут | включить архивацию WAL на сервере базы (`archive_mode=on`, `archive_command` в хранилище вне машины) и базовые копии `pg_basebackup`; восстановление на момент времени через `recovery_target_time`. Без этого потеря до суток |

Цели для владельца (решает владелец): допустимая потеря данных (RPO) и время восстановления (RTO). Ежедневная копия даёт RPO до 24 часов; с WAL
минуты. Проверено: цикл «копия → восстановление в пустую базу → проверка» на PostgreSQL 16, повторное восстановление в непустую базу отклоняется.

## 4. Мониторинг

`GET /metrics` (Prometheus, текст) включается `TIPS_METRICS_TOKEN` (не короче 24 символов; `Authorization: Bearer <токен>`); без токена маршрута нет.
Метрики не содержат идентификаторов, сумм и персональных данных. `GET /health` проверяет доступность базы (503, если недоступна).

| Метрика | Что значит | Оповещение |
|-|-|-|
| `tips_payments{status}` | платежи по статусам | резкий рост `DECLINED` относительно `SUCCESS` |
| `tips_oldest_pending_seconds` | возраст самого старого PENDING | больше 1200 (сверка должна закрывать за 15 минут: воркер стоит или банк не отвечает) |
| `tips_oldest_created_seconds` | возраст самого старого CREATED | больше 2400 (автоотмена должна срабатывать через 30 минут) |
| `tips_webhook_backlog` | события провайдера в очереди | больше 0 дольше 5 минут |
| `tips_webhook_stuck` | события, исчерпавшие 10 попыток | больше 0, нужен разбор |
| `tips_refunds_open` | возвраты в работе | растёт дольше часа |
| `tips_refunds_stuck` | возвраты, исчерпавшие 5 попыток | больше 0, ручной возврат (деньги плательщика) |

Журналы: строка доступа без query и без секретов, идентификатор запроса в `X-Request-ID`; необработанные ошибки пишутся с трассировкой без секретов.

## 5. Ротация ключей

| Ключ | Порядок |
|-|-|
| QR v2 (`TIPS_QR_KEYS`) | добавить новый ключ в список, сделать активным (`TIPS_QR_ACTIVE_KID`), через 4 часа (TTL QR) убрать старый |
| JWT (`TIPS_JWT_KID`, `TIPS_JWT_PRIVATE_KEY`) | новый ключ активным, открытая часть старого в `TIPS_JWT_RETIRED_PUBLIC_KEYS` на 15 минут (срок access-токена), затем убрать |
| Пароль базы | сменить в базе и в `.env`, перезапустить `app` и `worker` |
| Токен метрик | сменить в `.env` и в системе мониторинга |

## 6. Разбор происшествий

- **Платёж долго в PENDING.** Проверить воркер (`docker compose logs worker`), доступность провайдера, `tips_oldest_pending_seconds`. Сверка спрашивает банк и не закрывает вслепую; если банк не знает платёж 15 минут, он закрывается отказом.
- **Возврат застрял** (`tips_refunds_stuck` > 0). Найти в таблице `refunds` строки с `attempts >= 5`, сделать возврат в кабинете провайдера вручную, затем пометить `status='REFUNDED'` с идентификатором возврата провайдера. Это деньги плательщика: не оставлять без ответа.
- **События провайдера не обрабатываются** (`tips_webhook_stuck`). Смотреть `gateway_events.last_error`, исправить причину, обнулить `attempts` у нужных строк: воркер подхватит.
- **Блокировка гостей за общим Wi-Fi** (5 неверных подписей за 15 минут на пару «адрес и QR»). Это ожидаемая защита; QR выпускают заново.

## 7. Чего ещё нет

Реальный платёжный провайдер (нужен выбор и тестовый контур), автоматическая архивация WAL (настройка сервера базы), централизованный сбор журналов и
трассировка, обновление без простоя (сейчас перезапуск секунд на десять), нагрузочное тестирование.
