# API v2, адаптер провайдера, форма: дизайн

Составлен 2026-11-09, решения владельца учтены (`decisions.md`). Реализация идёт по шагам из раздела 9; после каждого шага все прежние тесты остаются зелёными.

## Решения по открытым вопросам (приняты разработчиком по поручению владельца)

| Вопрос | Решение |
|-|-|
| TTL QR v2 | 4 часа (настраивается), для v1 остаётся 24 часа |
| Выключение v1 | `TIPS_API_V1=off` при запуске в продакшен; пока включён |
| Непрозрачные id мерчантов и официантов | пока нет: их видит только персонал |
| Комиссия за автовозврат | на платформе (это защита от нашей двойной оплаты); условия уточнить в договоре с провайдером |
| Попыток возврата до передачи человеку | 5 |
| 3-D Secure | редирект (проще, не нужен iframe, `form-action` ограничивается адресом банка) |

## 1. Версии и общее ядро

- `/api/v2` отдельным роутером поверх тех же сервисов; версию QR определяет столбец `version` в базе, а не запрос. `create_app(enable_v1=True)`.
- Ядра `create_payment_core`, `issue_qr_core` не знают формата id и регэкспов; v1-функции остаются обёртками.
- v2 работает только на PostgreSQL. CLI и CSV остаются на v1.
- В v2 входят гостевые операции, выпуск QR и вебхуки. Персонал (вход, отчёты, статус мерчанта) пока общий.

## 2. Идентификаторы
128 случайных бит, base32 Crockford, нижний регистр, 26 символов: `qr_…`, `pay_…`, `rf_…`. Это сами первичные ключи (отдельного public_id нет). Не пересекаются с v1.

## 3. QR v2
- `nonce` 128 бит, `key_id`, TTL 4 часа.
- Подпись: `HMAC-SHA256(ключ kid, "tips-qr-v2" + поля с префиксами длины)[:16]` в base64url (22 символа). Поля: kid, qr_id, merchant_id, employee_id, receipt_id, amount, currency, nonce, exp.
- Ключи: `TIPS_QR_KEYS="kid:base64key,…"`, активный `TIPS_QR_ACTIVE_KID`; проверка по kid строки БД одним сравнением.
- Ссылка `https://<front>/p#q=<qr_id>&s=<sig>`: фрагмент не уходит на сервер и в журналы.
- Нет понижения версии: v1 принимает только `version=1`, v2 только `version=2`.

## 4. Деньги в v2
Строки `^(0|[1-9][0-9]{0,6})\.[0-9]{2}$`; число или bool в поле денег это ошибка формата. Ответы через `fmt()`.

## 5. Провайдер
Интерфейс `PaymentProvider`: `create_payment`, `get_status`, `void`, `refund`, `parse_webhook`; результат `SUCCEEDED|FAILED|PROCESSING|ACTION_REQUIRED|NOT_FOUND`. Ключ идемпотентности у провайдера и `reference` это `payment_id`. Вызовы провайдера идут вне транзакции.

Подтверждение: CREATED → PENDING; если на QR уже есть SUCCESS, платёж отменяется (`QR_USED`); результат: 200 SUCCESS, 402 DECLINED, 202 PENDING (в том числе 3-D Secure со `next_action`). Опрос статуса сам обновляет PENDING у провайдера.

Вебхук: подпись `t=<unix>,v1=<hex>` с допуском ±300 с, дедупликация в `gateway_events`, ответ 200 сразу, обработка по возможности и воркером; тело события лишь подсказка, истину даёт `get_status`. Поздний успех после DECLINED или CANCELED фиксируется; если на QR уже есть другой SUCCESS, платёж уходит в `REFUND_PENDING` и в той же транзакции появляется запись `refunds` (outbox); воркер вызывает возврат, после 5 неудач передаёт человеку.

## 6. Песочница
Модуль «банка» (автомат с токеном карты, 3-D Secure, вебхуками, возвратом); тестовые карты `…4242` успех, `…0002` отказ, `…3220` 3-D Secure, `…0119` таймаут (банк списал, ответа нет). Обёртка внутри процесса для тестов и страницы песочницы для формы; запрещена при `TIPS_ENV=production`.

## 7. Форма
`web/pay/` без сборки: HTML, ES-модуль, CSS. Поля карты в iframe провайдера, токен через `postMessage` с проверкой `origin`. Отдельный CSP для `/pay/*`. На клиенте не хранятся: PAN и CVC (их не видит наш код), JWT и refresh, ключ идемпотентности после завершения; пара `{payment_id, confirm_token}` только в `sessionStorage` на время редиректа 3-D Secure.

## 8. Найденные риски в существующем коде (учтены в v2)
1. `charge/lookup` шлюза привязаны к `(qr_id, nonce)`: с реальным провайдером повторная попытка после отказа получит тот же ключ. v1 остаётся только на эмуляторе.
2. Повтор с тем же ключом выдаёт новый `confirm_token`, поэтому ключ работает как секрет: в v2 строго UUIDv4 в заголовке `Idempotency-Key`.
3. Подтверждение не проверяет, есть ли на QR SUCCESS: в v2 проверка добавлена.
4. Глобальный лимит по адресу задушит всплески вебхуков: путь вебхуков исключается из него до проверки подписи.
5. Гостевой просмотр QR отдаёт `merchant_id` и `employee_id`: в v2 убрать.
