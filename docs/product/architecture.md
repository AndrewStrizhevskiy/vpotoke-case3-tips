# Продукт «Чаевые»: из прототипа в сервис

Проект дизайна для ветки `product/foundation`. Составлен 2026-11-09 по материалам репозитория; решения, помеченные как «решение владельца», принимает команда. Исходные ADR-001…009 остаются описанием хакатонного прототипа: там, где ниже сказано «ошибка ADR», действует этот документ.

Исходные условия: эмулятор шлюза остаётся, но за интерфейсом, который позже заменяется реальным провайдером; разработка идёт силами одного разработчика.

## 1. Стек

Python 3.12, FastAPI, Pydantic v2, PostgreSQL 16, SQLAlchemy 2.0, Alembic, psycopg 3, Redis (только для rate limit), PyJWT, argon2-cffi.

- Python 3.9 (локально сейчас) вышел из поддержки в октябре 2025, CI идёт на 3.12. Код пишется совместимым с 3.9, пока локальный интерпретатор не обновлён.
- Слой БД синхронный: эндпоинты `def`, транзакции и `FOR UPDATE` проще писать и тестировать. Нагрузка небольшая. Async при необходимости затрагивает только адаптеры.
- Фоновые задачи — отдельный процесс-воркер без Celery: цикл и `SELECT … FOR UPDATE SKIP LOCKED`.

## 3. Схема PostgreSQL

Деньги `NUMERIC(12,2)`, время `timestamptz`, статусы `text CHECK (…)`.

- `merchants(merchant_id PK, name, status CHECK IN (ACTIVE, BLOCKED, PENDING))`.
- `employees(employee_id PK, merchant_id FK, name, payout_mask CHECK ~ '^\*{4}\d{4}$')`, `UNIQUE(employee_id, merchant_id)` как цель составного FK.
- `receipts(merchant_id, receipt_id, amount CHECK 0 < amount <= 1000000, currency, PK(merchant_id, receipt_id))`.
- `qr_codes(qr_id PK, merchant_id, employee_id, receipt_id, nonce, exp, signature, key_id, created_at)`: составной `FK(employee_id, merchant_id)` (официант работает у этого мерчанта), `FK(merchant_id, receipt_id)`, `CHECK(exp <= created_at + 24 h)`.
- `payments`: `payment_id PK`, `qr_id FK`, `merchant_id`, `employee_id`, `amount`, `tip`, `amount_total`, `currency`, `status`, `error_code`, `idempotency_key uuid`, `request_hash`, `confirm_token_hash`, `provider`, `provider_payment_id`, `created_at`, `submitted_at`, `finalized_at`, `version`.
  - `CHECK(tip >= 0 AND tip <= amount * 0.5 AND amount_total = amount + tip AND amount_total <= 2000000)`.
  - `UNIQUE(qr_id, idempotency_key)`.
  - `UNIQUE INDEX one_success ON payments(qr_id) WHERE status = 'SUCCESS'` (nonce гасится на SUCCESS).
  - `UNIQUE INDEX one_active ON payments(qr_id) WHERE status IN ('CREATED','PENDING')`: блокировка QR из ADR-002 на уровне БД. Без неё два одновременных запроса с разными ключами создадут два CREATED.
  - `UNIQUE(provider, provider_payment_id)`; индексы по `(merchant_id, created_at)`, `(employee_id, created_at)`, частичный `(status, submitted_at)` для воркера.
- `audit_events(event_id bigserial PK, payment_id FK, qr_id, action, from_status, to_status, amount_total, actor, at)`: только дописывается (`REVOKE UPDATE, DELETE` у роли приложения плюс триггер).
- `gateway_events(provider, event_id, payload jsonb, received_at, processed_at, PK(provider, event_id))`: входящий ящик вебхуков, дедупликация.
- `users(id, login, password_hash, role, merchant_id, employee_id, status)`, `refresh_tokens(id, user_id, token_hash, expires_at, revoked_at)`.
- Таблицы Report нет: отчёт считается из `payments` (ADR-007).

Транзакции:
- **Создание:** `SELECT … FROM qr_codes WHERE qr_id = … FOR UPDATE` → поиск по ключу → проверки → `INSERT payment` + `INSERT audit` → `COMMIT`. Нарушение уникальности переводится в код: `(qr_id, key)` — ответ как на повтор, `one_active` — `PAYMENT_IN_PROGRESS`, `one_success` — `QR_USED`.
- **Переход статуса:** `UPDATE payments SET status = :new, version = version + 1 WHERE payment_id = :id AND status = :expected RETURNING …` и аудит в той же транзакции. 0 строк — перечитать и ответить по таблице повторов.
- **Вызов шлюза вне транзакции:** tx1 CREATED→PENDING и коммит, затем вызов шлюза с `idempotency_key = payment_id`, затем tx2 записывает итог условным UPDATE.

## 4. Ошибки и пробелы ADR, которые нужно исправить

Небезопасно для продакшена:

1. **Сверка PENDING → DECLINED через 15 минут без вопроса шлюзу (ADR-001/002).** Если банк всё же списал деньги, клиент заплатил, QR свободен, возможна вторая оплата. Сверка должна вызывать `gateway.get_status()`, закрывать платёж DECLINED только при подтверждённом отказе или когда шлюз платёж не знает, иначе эскалировать. Сетевая ошибка при `charge` — всегда PENDING. Нужна политика «позднего успеха» (вебхук SUCCESS после DECLINED/CANCELED). *В прототипе правило остаётся учебным.*
2. **`confirm_token` нельзя вернуть повторно (ADR-003):** хранится только SHA-256. При повторе POST /tips с тем же ключом и тем же `request_hash` выпускается новый токен и заменяет хеш. `idempotency_key` становится данными «на предъявителя»: строго UUIDv4 на сервере, не пишется в логи.
3. **`confirm_token` в query у `GET /payments/{id}` утекает в логи и Referer.** Переносится в заголовок `X-Payment-Token`; проверка `hmac.compare_digest(sha256(token), stored)` в HTTP-зависимости, домен о токене не знает.
4. **Nonce из 6 hex с UNIQUE:** коллизии примерно с ~4 тыс. QR. Для новых QR не менее 64 бит, UNIQUE по nonce снимается.
5. **ID в контракте ограничены и последовательны** (`^p_[0-9]{4}$`, `^qr_[0-9]{3}$`): потолок и перебор. Нужны непрозрачные ID (префикс + ULID/UUIDv7).
6. **Деньги в JSON как float** (`money_json`, `round_money`): в API v2 строки-десятичные.
7. **Подпись обрезана до 64 бит, `kid` нет.** Для seed-данных допустимо; для новых QR payload v2 с `v`, `kid` и 128 битами.
8. **Блок по IP после 5 неверных подписей:** за NAT ресторана один злоумышленник блокирует всех гостей. Лимит по связке IP + `qr_id`, скользящее окно.
9. **Автоотмена CREATED при hosted-форме:** клиент мог уже заплатить на странице провайдера. Отмена (ручная и автоматическая) сначала делает `gateway.cancel()` (void), затем меняет статус; окно автоотмены больше 15 минут из-за 3DS.

Не реализовано в прототипе:
- **JWT:** подпись ES256/EdDSA с `kid`; access 15 минут, refresh хранится хешем и ротируется; claims `sub`, `role`, `merchant_id`, `employee_id`, `iss`, `aud`, `exp`, `jti`; алгоритмы в `decode` фиксируются явно.
- **RBAC:** матрица прав из `docs/11-security.md` одной таблицей политик; владелец ресурса берётся из claims, а не из параметров запроса.
- **Rate limit:** грубые лимиты на границе (nginx/WAF) плюс библиотека `limits` с Redis; 429 `RATE_LIMITED` и `Retry-After`.
- **Секреты:** интерфейс `SecretProvider` (dev — env, прод — secret manager), HMAC-ключи как keyring `{kid: key}`: подписываем активным, проверяем всеми действующими. Маскирование логов фильтром.
- **Воркер:** `auto_cancel` и `reconcile` пачками через `SKIP LOCKED`; время отправки берётся из `payments.submitted_at`, а не из скана аудита.

## 5. Интерфейс платёжного шлюза

```python
class PaymentGateway(Protocol):
    def charge(self, req: ChargeRequest) -> ChargeResult: ...
    #  req: payment_id (он же ключ идемпотентности у провайдера), amount: Decimal, currency,
    #       payment_method_token | None (одноразовый токен из hosted fields), return_url, metadata
    #  result: status in {SUCCEEDED, FAILED, PENDING, ACTION_REQUIRED}, provider_payment_id,
    #          error_code in {CARD_DECLINED, GATEWAY_TIMEOUT, ...}, action_url
    def get_status(self, provider_payment_id: str) -> ChargeResult: ...
    def cancel(self, provider_payment_id: str) -> ChargeResult: ...   # void до списания
    def parse_webhook(self, headers, body: bytes) -> GatewayEvent: ...  # проверяет подпись
```

Эмулятор игнорирует токен и считает исход по `metadata` через `emulate_gateway`. Реальный провайдер: карту клиент вводит в iframe провайдера, на сервер приходит только токен (PCI SAQ A); на странице оплаты строгий CSP и SRI. Контракт расширяется полем `payment_method_token` и ответом 202 с `action_url` (3DS). Вебхук: `INSERT` в `gateway_events` (конфликт — уже обработано), затем условный UPDATE статуса. Один набор контрактных тестов гоняется на эмуляторе и на sandbox провайдера.

## 7. Решения владельца (не архитектора)

1. **Юридическая схема денег:** кто держит средства (сплит и выплаты у провайдера, эквайринг мерчанта или агрегатор по 161-ФЗ), чеки по 54-ФЗ, налоги официантов. От этого зависит выбор провайдера.
2. **Провайдер:** hosted fields, void, `get_status`, подписанные вебхуки, выплаты физлицам.
3. **Источник реестра чеков (ADR-003):** с какими POS интегрироваться (iiko, r_keeper и т. д.). Без этого нет «серверной правды» о сумме.
4. **API v2:** ломать контракт сейчас (непрозрачные ID, деньги строками, токен в заголовке, payload QR v2) или держать совместимость с тестовыми векторами хакатона как legacy-режим.
5. **Поздний успех и двойная оплата:** автовозврат или ручной разбор, кто платит за возвраты; хостинг в РФ (152-ФЗ), целевой SLA.

Допущения, которые не проверялись: нагрузка небольшая, один регион, у провайдера есть токенизация и void.

### M2: что реализовано и чем отличается от проекта выше

- Те же 18 приёмочных тестов (`prototype/run_tests.py`) и 61 команда эталонного сценария (`tests/golden_cli.py`) дают одинаковый результат на CSV и на PostgreSQL. Исключение одно: проверка «confirm без QR» относится к CSV-режиму (QR в другом файле) и в SQL не выполняется.
- Параллельность (`tests/test_postgres.py`, 13 тестов): 20 одновременных создания платежей на один QR с разными ключами дают ровно один платёж и 19 `PAYMENT_IN_PROGRESS`; 20 запросов с одним ключом дают один платёж; 10 параллельных confirm вызывают шлюз один раз; гонка cancel и confirm приходит к одному согласованному состоянию; параллельная сверка закрывает платёж один раз; `UPDATE`, `DELETE` и `TRUNCATE` в `audit_events` запрещены.
- Защита двойной оплаты двухслойная: блокировка строки QR (`FOR UPDATE`) выстраивает запросы в очередь, а уникальные индексы `payments_one_active` и `payments_one_success` не дают записать второй платёж, даже если блокировку убрать. Это проверено «мутацией»: без блокировки тесты проходят благодаря индексу, без блокировки и без индекса падают (5 платежей вместо одного).
- Переход статуса условный (`UPDATE … WHERE status = :старый`): проигравший гонку получает `StateChanged` и отвечает как на повторный запрос; шлюз вызывается только после успешного перехода в PENDING.

Отличия от раздела 3:

- `idempotency_key` хранится как `text`, а не `uuid`: прототип и контракт принимают любую непустую строку. Ужесточение до UUIDv4 войдёт в API v2 (раздел 4, пункт 2).
- Идентификаторы `p_NNNN` выдаются последовательностью `payment_seq` (с 101). При откате транзакции номер пропадает, подряд идущими они остаются только без сбоев.
- `CHECK (tip <= amount * 0.5 + 0.005)`: полкопейки добавлены, потому что чаевые 50 % от очень малой суммы округляются вверх (0,01 от 0,01), и прототип такой платёж разрешает.
- История платежей из seed-данных лежит в отдельной таблице `seed_payments` (только для отчётов): в CSV-режиме она тоже не влияет на блокировку QR и погашение nonce.
- `qr_codes.created_at` считается как `exp - 24 ч`, пока в сервисе нет собственного времени выпуска.
- Не сделано в M2: роли БД с `REVOKE UPDATE, DELETE` (аудит защищён триггером), `request_hash`, `confirm_token_hash`, `gateway_events`, пользователи (M3–M6).

### M3: HTTP API

Приложение: `python -m tips.http` (нужны `TIPS_DATABASE_URL`, `TIPS_HMAC_SECRET`; порт 8083 из контракта, `TIPS_HOST`, `TIPS_PORT`). Работает только поверх PostgreSQL: токен платежа и журнал статусов мерчанта хранятся в базе (миграция `0002`).

Все 10 путей контракта реализованы тонким слоем над теми же сервисами, что и CLI. Тела запросов читаются как есть и проверяются теми же функциями (суммы идут в `Decimal`: 637.005 даёт 400, а не тихое округление до 637.00). Ответы и коды ошибок проверяются тестами по `api/05_api_schemas.yaml`: тело проходит схему, а код описан для операции.

Что изменено в контракте (версия 1.1) и почему:

| Изменение | Причина |
|-|-|
| `TipCreate.sig` обязателен | в контракте подписи в теле запроса не было, и по подряд идущим `qr_id` можно было создавать платежи по чужим чекам; подпись проверяется первой (ADR-003, ADR-004) |
| статус платежа читается с заголовком `X-Payment-Token`, а не параметром `confirm_token` | параметры адреса попадают в логи и в Referer |
| 401 для защищённых операций | нет учётных данных; 403 остаётся для «прав не хватает» |
| 400 для confirm, cancel, чтения статуса и отчётов; 404 для отчётов | формат запроса и несуществующий мерчант или официант |

Токен платежа: 128 случайных бит (32 hex), в базе только SHA-256, сравнение за постоянное время. Чужой токен и несуществующий платёж дают один и тот же 404. Токен показывается один раз; при повторе `POST /tips` с тем же ключом и тем же телом выдаётся новый токен, а старый перестаёт работать (иначе клиент, потерявший ответ 201, терял бы платёж). `idempotency_key` строго UUID, это одновременно секрет повтора.

Что сознательно не сделано в M3:

- **Аутентификация.** Правила доступа (кто выпускает QR, чьи отчёты видны, кто меняет статус мерчанта) реализованы окончательно и проверены тестами, но источник личности временный: заголовки `X-Dev-Role`, `X-Dev-Merchant`, `X-Dev-Employee`, и только при `TIPS_DEV_AUTH=1`. По умолчанию защищённые операции отвечают 401. В M4 здесь появятся JWT и вход; без M4 сервис в интернет выпускать нельзя.
- **Лимиты запросов, журналы без секретов, CORS, TLS** (M5).
- **Гонка при выпуске QR:** номер QR вычисляется как «последний + 1», два одновременных выпуска дадут конфликт ключа (ошибка 500). Нужна последовательность в базе, исправление войдёт в M5.
- **Выпуск QR берёт сумму только из реестра чеков** (контракт не принимает `amount`); реестр пока наполняет seed и CLI. Интеграция с кассой (POS) остаётся решением владельца.
- **Ответ 202 с `action_url`** (3DS) и `payment_method_token` появятся с реальным провайдером (M6).
- Ключ `idempotency_key` в CLI по-прежнему любая строка, в HTTP только UUID.

Тесты: `tests/test_http.py` (33): сценарии T3 через HTTP, проверка токена (чужой, угаданный, короткий, в адресе), форма чаевых, ошибки без раскрытия, права по ролям, блокировка мерчанта с записью в журнал, 12 параллельных запросов на один QR (ровно один платёж), 8 параллельных confirm (шлюз вызван один раз). Проверено «мутациями»: если отключить проверку токена, проверку роли администратора, права на отчёты или аутентификацию, соответствующие тесты падают.

### M4: вход и роли

Временные заголовки `X-Dev-*` и переменная `TIPS_DEV_AUTH` удалены целиком: вход возможен только по логину и паролю.

Запуск сервиса теперь требует ключ подписи. Выпуск и пользователи:

```bash
python3 -m tips.http.keys k2026-11          # печатает TIPS_JWT_KID и TIPS_JWT_PRIVATE_KEY, их задайте сервису
export TIPS_DATABASE_URL=postgresql://…  TIPS_HMAC_SECRET=…
python3 -m tips.adapters.sql.admin migrate
python3 -m tips.adapters.sql.admin create-user --login boss --role admin
python3 -m tips.adapters.sql.admin create-user --login ivanov --role waiter --merchant m_001 --employee e_001
python3 -m tips.adapters.sql.admin set-password --login ivanov        # отзывает все входы пользователя
python3 -m tips.adapters.sql.admin disable-user --login ivanov
python3 -m tips.http                                                  # сервис на порту 8083
```

Пароль запрашивается без вывода на экран (или берётся из `TIPS_NEW_PASSWORD`), в аргументах командной строки и в журналах его нет. Первого администратора создаёт тот, у кого есть доступ к базе и окружению сервиса.

Как устроено:

| Что | Решение |
|-|-|
| Пароли | argon2id (параметры библиотеки по умолчанию), NFKC-нормализация, длина 12–128, не содержит логин, не повторяющийся и не из распространённых слов; хеш обновляется при входе, если параметры ужесточили |
| Access-токен | JWT ES256 на 15 минут; claims `iss`, `aud`, `sub`, `role`, `merchant_id`, `employee_id`, `iat`, `exp`, `jti`; в заголовке `kid` |
| Проверка токена | алгоритм зафиксирован (alg=none, HS256 и всё, кроме ES256, отвергаются до проверки подписи), `kid` должен быть в связке ключей, обязательные claims, сроки проверяются по внедряемым часам с допуском 5 с |
| Пользователь в базе | при каждом запросе сверяется со статусом и ролью из токена: закрытый или переведённый на другую роль пользователь теряет доступ сразу, а не через 15 минут; токен, выданный до смены пароля, тоже отвергается (`iat` раньше `password_changed_at`) |
| Refresh-токен | 256 случайных бит, в базе только SHA-256, живёт 14 дней, при обновлении заменяется; цепочка одного входа живёт не дольше 30 дней |
| Кража refresh | повторное предъявление уже использованного токена отзывает всю цепочку (окно 10 с на повтор того же запроса при потере ответа) |
| Перебор паролей | 5 неудач подряд блокируют вход на 15 минут (неудача старше 15 минут не считается); неизвестный логин, неверный пароль, закрытая и заблокированная учётная запись дают один ответ 401, время выравнивается пробным хешированием, неудачи по неизвестным логинам пишутся в журнал без самого логина |
| Перегрузка хешированием | одновременно не больше 4 операций argon2: остальным 429 `RATE_LIMITED` с `Retry-After`; поток запросов на вход не исчерпает память и процессор |
| Порядок блокировок | везде «пользователь, затем его токены»: вход, обновление, выход, смена пароля и закрытие не обходят друг друга и не блокируются взаимно; вход перепроверяет пароль под блокировкой, поэтому смена пароля во время входа не пропускает старый пароль и не откатывается обновлением хеша |
| Администраторы | последнего действующего администратора закрыть нельзя; `enable-user` возвращает закрытого пользователя; действия администратора в журнале записаны с его `user_id` |
| Ротация ключа подписи | `TIPS_JWT_KID` и `TIPS_JWT_PRIVATE_KEY` новые, старый открытый ключ добавляется в `TIPS_JWT_RETIRED_PUBLIC_KEYS` (JSON `{kid: PEM}`) на время жизни токенов (15 минут), затем удаляется |
| Журнал входа | `auth_events` только дописывается; в нём пользователь, действие и время, без паролей и введённых логинов |
| Ответы с токенами | `Cache-Control: no-store` |

Права по ролям (кто что видит и делает) не менялись с M3, но теперь опираются на проверенный токен. Матрица проверяется тестом «роль × операция» для 5 ролей и 10 операций, плюс отдельно запрос без токена.

Проверено «мутациями»: если отключить проверку подписи, срока, сверку с пользователем в базе, отзыв цепочки refresh, блокировку входа или отзыв сессий при смене пароля, соответствующие тесты падают.

Независимое ревью безопасности (отдельный рецензент, только чтение) критичных дыр не нашло: подмена алгоритма, поддельные токены, обход прав и SQL-инъекции не обнаружены. Найденное средней важности исправлено и закрыто тестами: перегрузка хешированием, гонка отзыва сессий при смене пароля, откат пароля при обновлении хеша, access-токен после смены пароля, личность администратора в журнале, затухание счётчика неудач, закрытие последнего администратора. Каждое исправление проверено «мутацией» (без него соответствующий тест падает).

Принятые остаточные риски (записаны намеренно):

- Блокировка учётной записи после 5 неудач позволяет тому, кто знает логин, мешать его владельцу входить (особенно администратору). Смягчит лимит по адресу и логину в M5; для администраторов позже можно заменить жёсткую блокировку нарастающей задержкой.
- Проверка блокировки не атомарна с подсчётом неудач: пачка одновременных запросов может сделать больше 5 попыток (не больше числа потоков сервера).
- Блокировка мерчанта закрывает выпуск QR и платежи, но отчёты мерчанта и официанта остаются доступны; уволенный официант работает, пока администратор не выполнит `disable-user`.
- Пароль может передаваться через `TIPS_NEW_PASSWORD` и тогда виден в окружении процесса: для автоматизации, не для ручной работы.

Что сознательно не сделано в M4:

- **Ограничение частоты запросов** (в том числе на `/auth/login` по IP): M5. Пока перебор по одному логину ограничен блокировкой, перебор по многим логинам одним паролем нет. Блокировка учётной записи позволяет злоумышленнику, знающему логин, мешать его владельцу входить (компромисс осознанный; IP-лимиты M5 его смягчат).
- **Двухфакторная аутентификация, восстановление пароля, самостоятельная регистрация**: пользователей заводит администратор платформы.
- **Роли БД с `REVOKE`** для журналов: защита триггером.
- **TLS, CORS, заголовки безопасности**: M5.

### M5: эксплуатация сервиса

Запуск: HTTP-сервис `python -m tips.http` и отдельный воркер `python -m tips.jobs.worker` (флаги `--once`, `--interval 30`).

| Что | Решение |
|-|-|
| Сверка зависших платежей | воркер спрашивает шлюз (`lookup`), а не закрывает платёж отказом по одному времени: `SUCCESS` и `DECLINED` переносятся как есть, «шлюз платёж не получал» закрывает как `DECLINED/GATEWAY_TIMEOUT`, «ещё в обработке» оставляет PENDING; дольше суток такой платёж попадает в журнал ошибок для ручного разбора. Это исправляет опасное правило ADR-001/002: если банк всё же списал деньги, платёж больше не закрывается отказом и QR не освобождается для второй оплаты |
| Восстановление после сбоя | процесс упал между переходом в PENDING и записью ответа шлюза: через 15 минут сверка узнаёт настоящий исход, а не угадывает отказ |
| Автоотмена | CREATED, не подтверждённый 30 минут, отменяется (запас на 3-D Secure, ADR-002 говорил о 15); сначала `void` у шлюза, потом статус, действует «система», событие в аудите |
| Воркер | задачи независимы (сбой одной не мешает остальным); несколько копий безопасны, переходы условные; чистит счётчики лимитов старше суток |
| Лимиты запросов | счётчики фиксированных окон в PostgreSQL (`rate_hits`), без Redis: при небольшой нагрузке этого достаточно, при росте заменяется за интерфейсом `LimitStore`. Правила: 300/мин на адрес (кроме `/health`), просмотр QR 30/мин, создание платежа 10/мин на адрес и QR, confirm и cancel 10/мин на адрес и платёж, статус 30/мин, вход 10/мин, обновление 20/мин, защищённые операции 120/мин на пользователя. 429 с `Retry-After` до конца окна |
| Неверные подписи | 5 неверных на пару «адрес и qr_id» блокируют её на 15 минут (подбор 64-битной подписи нереален, а гости за общим Wi-Fi остальных QR не теряют) |
| Адрес клиента | за прокси берётся запись `X-Forwarded-For`, добавленная нашим прокси, отсчёт справа (`TIPS_TRUSTED_PROXY_HOPS`); без доверенного прокси заголовок игнорируется; IPv6 сводится к /64 |
| Номера QR | последовательность базы `qr_seq`: два одновременных выпуска больше не получают один номер |
| Ключи HMAC QR | `TIPS_HMAC_SECRET` подписывает, `TIPS_HMAC_SECRET_PREVIOUS` (через запятую) только проверяет на время жизни QR; ротация без простоя |
| Журналы | в строке доступа только метод, путь без query, код, время, адрес и идентификатор запроса; каждая строка проходит очистку (подписи, токены, JWT, пароли, длинные hex, номера карт по Luhn); стандартный access-лог uvicorn выключен, потому что в нём адрес с подписью; параметры запросов в ошибках базы скрыты |
| Необработанные ошибки | клиенту всегда общий `500 INTERNAL_ERROR`, подробности только в журнале и без секретов |
| Заголовки и CORS | `nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'`, `Cache-Control: no-store`, HSTS в production; CORS выключен, включается списком `TIPS_CORS_ORIGINS` (звёздочка запрещена); `X-Request-ID` принимается только безопасного вида |
| Размер тела | не больше 64 КиБ, проверяется и по длине, и потоком (тело без длины тоже) |
| Документация API | `/docs`, `/redoc`, `/openapi.json` отключены, если `TIPS_ENV` не `development` (по умолчанию production) |
| Контракт | у каждой операции описаны 429 и 500 (`INTERNAL_ERROR`) |

TLS заканчивается на прокси или балансировщике перед сервисом; сам сервис по HTTP внутрь сети, наружу его выставлять нельзя.

Независимое ревью M5 (отдельный рецензент, только чтение) нашло две серьёзные проблемы и ряд средних. Всё исправлено и закрыто тестами; каждое исправление проверено «мутацией» (без него тест падает):

- **Номера после 999 и 9999.** `lpad` в PostgreSQL обрезает длинные числа справа: `qr_1000` превращался в `qr_100`, уже занятый, и выпуск зацикливался навсегда; то же ждало платежи (`p_10000`) и события аудита. Форматирование перенесено в Python, число попыток ограничено, шаблоны идентификаторов в контракте расширены до `{3,12}` и `{4,12}`.
- **Два QR на один чек.** Двойной клик официанта выпускал два живых QR на один чек, и каждый можно было оплатить отдельно. Выпуск теперь идёт в транзакции под блокировкой строки чека; в тесте на 10 одновременных запросов без блокировки получалось 7 разных QR, с блокировкой один.
- Подпись не из ASCII давала 500 для существующего `qr_id` и 422 для несуществующего (оракул перебора), теперь одинаковый 422.
- Ключи лимитов: идентификатор платежа из пути без проверки позволял создавать строку счётчика на каждое значение и ронять вставку слишком длинным ключом; теперь мусорные значения делят один счётчик.
- IPv4-адреса в виде `::ffff:1.2.3.4` (сервис слушает `::`) сводились к одному адресу и делили лимит; теперь это обычные IPv4. Заголовок `X-Forwarded-For` читается по всем строкам.
- Заблокированный клиент больше не пишет в базу: отказ отдаётся из памяти до конца окна. `/health` проверяет базу (503 при недоступности).
- Сверка и автоотмена обрабатывают платежи по одному: сбой на «ядовитом» платеже не блокирует остальные, проход ограничен пачкой в 200. Для шлюза с запаздывающими данными задаётся `not_found_grace`: «платёж неизвестен» закрывает платёж только после дополнительного ожидания. Состояние «выяснить не удалось» (`UNKNOWN`) трактуется как «в обработке».
- Журналы: очистка вынесена в форматтер и не меняет запись для других обработчиков; переводы строк и управляющие символы в сообщениях экранируются (путь с `%0A` не подделает вторую строку); токены любой кодировки от 32 символов маскируются без ключевого слова; воркер использует тот же форматтер.
- CORS-заголовки теперь есть и у ответов самой обвязки (429, 500), а CSP не мешает Swagger UI в development; длина тела с не-ASCII цифрами не роняет сервис.

Принятые остаточные риски:

- Блокировка пары «адрес и qr_id» после 5 неверных подписей может задеть гостей за общим Wi-Fi, если кто-то из них набрал неверный код; остальные QR работают.
- За прокси нужно задать `TIPS_TRUSTED_PROXY_HOPS` (число прокси перед сервисом): по умолчанию 0, и тогда все клиенты видны как адрес прокси и делят лимиты. Если значение больше реального числа прокси, клиент может подделать адрес.
- Лимит входа считается по адресу, а не по логину: перебор одной учётной записи с множества адресов останавливает блокировка аккаунта и стоимость argon2.
- Лимитер пишет в основную базу (1–3 записи на запрос) и держит кэш отказов в памяти процесса; при заметном росте нагрузки счётчики переносятся в Redis или на прокси.
- `cancel_stale` сначала делает `void` у шлюза и только потом меняет статус: если `void` не удаётся, платёж остаётся CREATED и QR занят, но деньги клиента не теряются (обратный порядок мог бы потерять оплату); такие платежи старше суток попадают в журнал ошибок.
- Одноразовый код QR (`nonce`) по-прежнему 6 hex-символов (формат задан контрактом организаторов); защита от подбора держится на подписи, лимитах и блокировке.

Что осталось и что решать владельцу:

- **Реальный шлюз.** Интерфейс `PaymentGateway` теперь включает `lookup` и `void`; для эмулятора «таймаут» означает «банк запрос не получил». Настоящий провайдер подключается адаптером с тем же интерфейсом (M6).
- **Лимиты при росте нагрузки:** запись счётчика на каждый запрос это нагрузка на базу; при росте переносится в Redis или на прокси.
- **Формат идентификаторов** `qr_NNN`, `p_NNNN` ограничен контрактом (999 QR, 9999 платежей) и последовательный: нужен API v2.
- **Деплой**: образ, миграции при выпуске, секреты из менеджера секретов, бэкапы с восстановлением на момент времени, метрики и алерты на платежи в PENDING дольше суток: M7.


### API v2: провайдер, форма чаевых, песочница, проверки production

Проект: [v2-design.md](v2-design.md). Контракт: [api/v2.yaml](../../api/v2.yaml) (v1 остаётся в `api/05_api_schemas.yaml`).

| Что | Решение |
|-|-|
| Контракт v2 | `api/v2.yaml` (OpenAPI 3.0.3): непрозрачные id, деньги строками, `Idempotency-Key` заголовком, `next_action` для 3-D Secure, статусы `REFUND_PENDING`/`REFUNDED`. `tests/test_v2_contract.py` прогоняет все 26 сценариев `test_v2_http.py` через клиент, который проверяет каждый ответ по схеме и описанному коду; мутация (лишнее поле в ответе) роняет 12 сценариев |
| Форма чаевых | `web/pay/` (HTML + ES-модуль + CSS, без сборки и сторонних библиотек), отдаётся сервисом по `/p`, `/p/result`. 4 экрана макета; деньги в целых копейках; ключ идемпотентности UUIDv4 один на попытку; кнопка блокируется на время запроса; данные сервера выводятся через `textContent`; в `sessionStorage` только `{payment_id, confirm_token}`; номер карты и CVC очищаются из полей сразу после получения токена |
| Политика безопасности страниц | у `/p/*` свой CSP: скрипты и стили только `'self'`, соединения только `'self'`, формы только на свой узел, без `unsafe-inline`/`unsafe-eval`, `frame-ancestors 'none'`. Узлы провайдера добавляются через `TIPS_PROVIDER_CSP` (только `https://узел[:порт]`, остальное отбрасывается). Файлы читаются один раз при старте |
| Песочница банка | `/sandbox` (поля карты → токен `POST /sandbox/tokens`, страница 3-D Secure, кнопка «банк ответил на потерянные платежи»). Подключается только если `TIPS_ENV=development` и провайдер `sandbox`; в production маршрутов нет (404). Тестовые карты: …4242 успех, …0002 отказ, …3220 3-D Secure, …0119 потерянный ответ. Банк живёт в памяти процесса: воркер сверки в другом процессе его не видит, для живой демонстрации сверку не запускают |
| Адрес 3-D Secure | `TIPS_SANDBOX_URL` задаёт, где открывается страница банка (например `http://localhost:8083/sandbox`); `http` принимается только для `localhost`/`127.0.0.1`, иначе ссылка не отдаётся клиенту (защита от открытого редиректа) |
| Ключи QR v2 | `python -m tips.http.keys qr [kid]` печатает `TIPS_QR_KEYS` и `TIPS_QR_ACTIVE_KID` (256 бит); ротация: добавить новый ключ в список, сделать активным, старый убрать через 4 часа (TTL QR) |
| Отключение v1 | `TIPS_API_V1=off` убирает гостевые операции v1 (вход и отчёты остаются) |
| Проверки production | `python -m tips.http` в production не стартует, если: ключ `TIPS_HMAC_SECRET` демонстрационный или короче 16 символов; `TIPS_API_V1` не `off`; нет или слабые `TIPS_QR_KEYS`; `TIPS_PROVIDER=sandbox`; `TIPS_FRONT_URL` не `https://`; нет ключей JWT или `TIPS_DATABASE_URL`; в `TIPS_CORS_ORIGINS` звёздочка или не-https. Проверки смотрят на окружение (`http/prodcheck.py`), поэтому тесты, собирающие приложение вручную, их не проходят и не страдают |

Как открыть живую демонстрацию локально: `TIPS_ENV=development TIPS_QR_KEYS=… TIPS_QR_ACTIVE_KID=… TIPS_SANDBOX_URL=http://localhost:8083/sandbox TIPS_FRONT_URL=http://localhost:8083/p python -m tips.http`, выпустить QR через `POST /api/v2/qr` и открыть `pay_url` в браузере. Сквозной сценарий (экраны 1–4, 3-D Secure, возврат на `/p/result`) пройден в настоящем браузере: консоль чистая, нарушений CSP нет.

Что осталось по v2: реальный адаптер провайдера (нужны выбор провайдера и тестовый контур; в CSP добавляется его узел, а поля карты заменяются его полями), перенос состояния песочного банка в базу, если понадобится демонстрация со сверкой воркером, M7 (деплой, бэкапы, метрики).

Независимое ревью среза (отдельный рецензент, только чтение): критичных проблем нет, три средних исправлены, часть низких тоже.

- **Поля карты в production.** Форма жёстко слала номер и CVC на `/sandbox/tokens`; в production такого маршрута нет, и карточные данные проходили бы через наш контур. Теперь сервер отдаёт `index.html` с флагом `data-sandbox` (1 только в песочнице); без него поля скрыты, оплата заблокирована, платёж не создаётся, номер карты на наш сервер не уходит.
- **Залипший платёж.** Платёж, созданный, но не дошедший до банка, держал QR до автоотмены (30 минут), а ключ идемпотентности «залипал». Теперь форма отменяет такой платёж (`/cancel`) при ошибке токена, подтверждения и при «Назад» и берёт новый ключ; у ошибок с `retryable` есть кнопка «Повторить».
- **Опрос статуса.** 429 и 5xx больше не показываются как итог: опрос продолжается с учётом `Retry-After` (шаг 3 с), заканчивается только на 404.
- Низкие: кнопка не включается обратно при переходе на 3-D Secure; чужой узел перехода не открывается молча, а даёт ошибку; варианты чаевых и предел берутся из ответа сервера; POST `/sandbox/*` с чужим `Origin` отклоняется; сбой одного вебхука при доставке не теряет остальные; проверки production требуют `TIPS_FRONT_URL` вида `https://узел/p` и уникальные `kid`.

Принятые остаточные риски: проверки production работают при запуске через `python -m tips.http` (запуск через `uvicorn --factory` их обходит); низкоэнтропийный ключ QR определить нельзя; жизненный цикл `confirm_token` (повтор создания инвалидирует прежний) описан в контракте текстом, тестируется в `test_v2_http`; `app.js` проверяется статически и вручную в браузере, автотеста в браузере нет.
