# Механизм эмуляции платежа — кейс 3

Заполненный шаблон `07_payment_emulator_template.md`. Подробные обоснования — в ADR-001
(эмулятор), ADR-002 (статусы), ADR-004 (проверки), ADR-006 (ошибки), ADR-008 (идемпотентность).
Все числа в примерах посчитаны скриптом по `qr_links.csv` и `payments.csv`.

## 1. Состояния платежа

- **CREATED** — платёж создан, суммы зафиксированы, в шлюз ещё не отправлен. QR заблокирован для других попыток.
- **PENDING** — клиент подтвердил оплату, запрос ушёл в шлюз, итога пока нет.
- **SUCCESS** — шлюз подтвердил списание. Статус финальный, nonce QR погашен.
- **DECLINED** — шлюз отказал (`CARD_DECLINED`) или сверка закрыла платёж по таймауту (`GATEWAY_TIMEOUT`). Статус финальный, денег не списано.
- **CANCELED** — платёж отменён до отправки в шлюз: клиентом или системой (истёк `exp`, 15 мин без confirm). Статус финальный.

Схема — `diagrams/states.png` (приложение A.3).

## 2. Матрица переходов

| Из состояния | В состояние | Условие |
|-|-|-|
| CREATED | PENDING | клиент вызвал `confirm` с верным `confirm_token` |
| PENDING | SUCCESS | эмулятор вернул SUCCESS (h = 0–7 или строка таблицы сценариев) |
| PENDING | DECLINED | эмулятор вернул h = 8 (`CARD_DECLINED`) **или** сверка: 15 мин без ответа (`GATEWAY_TIMEOUT`) |
| PENDING | PENDING | эмулятор вернул h = 9 (TIMEOUT): ответ 202, клиент опрашивает статус, ждём сверку |
| CREATED | CANCELED | клиент вызвал `cancel` **или** система: истёк `exp` / 15 мин без confirm |
| PENDING | CANCELED | **запрещён**: 409 `CANCEL_NOT_ALLOWED` — запрос уже в шлюзе, деньги могли списаться |
| SUCCESS | CANCELED | **запрещён**: 409 `CANCEL_NOT_ALLOWED` — возвраты в проект не входят |

Из финальных статусов (SUCCESS, DECLINED, CANCELED) переходов нет.

## 3. Шаги обработки платежа

| Шаг | Что проверяется / делается | При ошибке |
|-|-|-|
| 1. Валидация | формат id (`qr_NNN`, `r_NNNN`), типы, обязательные поля, ровно одно из `tip_pct` / `tip_amount`, UUID ключа | 400 `VALIDATION_ERROR`, платёж не создаётся |
| 2. Проверка QR и повтор | Q-1 подпись (`compare_digest`) → P-2 поиск по `idempotency_key`: найден — вернуть его платёж (200) или `IDEMPOTENCY_CONFLICT` (409) → Q-2 `exp ≥ now` → Q-3 по QR нет SUCCESS → Q-4 мерчант ACTIVE → Q-5 `receipt_id` совпадает с QR | 422 `INVALID_QR` / 410 `QR_EXPIRED` / 409 `QR_USED` / 403 `MERCHANT_BLOCKED` / 422 `RECEIPT_MISMATCH` |
| 3. Расчёт суммы | `base_amount` = сумма из реестра чеков → P-1 диапазон чека → Q-6 диапазон чаевых → расчёт в `Decimal` → P-3 итог ≤ 2 000 000 | 422 `AMOUNT_MISMATCH` / `AMOUNT_OUT_OF_RANGE` / `TIP_OUT_OF_RANGE` |
| 4. Создание | по QR есть CREATED/PENDING → отказ; иначе атомарно записать ключ + платёж CREATED + событие аудита | 409 `PAYMENT_IN_PROGRESS` |
| 5. Подтверждение | `confirm_token` верен, статус CREATED → PENDING, вызов эмулятора | 404; повторный confirm возвращает текущий статус с прежним кодом (202 / 200 / 402) без вызова шлюза; confirm для CANCELED → 409 `PAYMENT_STATE_CONFLICT` |
| 6. Результат | таблица сценариев, затем `h`: 0–7 SUCCESS, 8 DECLINED, 9 PENDING | 402 `CARD_DECLINED` / 202 `GATEWAY_TIMEOUT` (опрос `GET /payments/{id}`) |
| 7. Отмена | только из CREATED (P-4) | 409 `CANCEL_NOT_ALLOWED` из PENDING, SUCCESS и DECLINED; повторная отмена CANCELED → 200 |
| 8. Аудит | событие на каждый переход, в одной транзакции с ним; журнал только дописывается | если событие не записалось, откатывается и переход |

## 4. Формулы

```
tip_amount   = round_half_up(base_amount × tip_pct / 100, 2)      # Decimal, не float
amount_total = base_amount + tip_amount
h            = int(md5(qr_id + nonce).hexdigest(), 16) mod 10     # только если qr_id нет в gateway_scenarios.csv
SIGNATURE    = HMAC-SHA256(SECRET, "merchant_id|employee_id|receipt_id|nonce|exp").hexdigest()[:16]
```

`SECRET` берётся из `TIPS_HMAC_SECRET`; seed-данные подписаны демо-ключом `demo-secret-k3`.
MD5 здесь только раскладывает платежи по корзинам, на безопасность он не влияет.

Почему `Decimal`: `round(53.50 * 5 / 100, 2)` во float даёт 2.67, правильный ответ — 2.68.

## 5. Пример расчёта (qr_001)

Payload: `m_001|e_001|r_1001|c82561|2025-11-01T23:59:00Z` → подпись `68d0f361ac38c12b`, совпадает с `qr_links.csv`.

- base_amount = 637.00 (сумма чека r_1001, совпадает с `p_0001.amount`)
- tip_pct = 5
- tip_amount = 637.00 × 5 / 100 = **31.85**
- amount_total = 637.00 + 31.85 = **668.85**
- h = md5("qr_001c82561") = `31f24d57…` → mod 10 = **9**
- статус = **SUCCESS**: qr_001 есть в таблице сценариев (тест T3-1), поэтому формула h не применяется

Сверка с `payments.csv`: p_0001 — 637.00 / 31.85 / SUCCESS, совпадает полностью.

Почему нужна таблица сценариев: по формуле организаторов qr_001 получил бы h = 9, то есть TIMEOUT,
и тест T3-1 не прошёл бы. Это отступление записано явно (ADR-001), а не спрятано подбором хеша.

## 6. Пример DECLINED (qr_003)

Payload: `m_001|e_003|r_1003|4443ae|2025-11-01T23:59:00Z` → подпись `e42db7c2c59521c8`, совпадает с `qr_links.csv`.

- base_amount = 911.00 (сумма чека r_1003, совпадает с `p_0003.amount`)
- tip_pct = 15
- tip_amount = 911.00 × 15 / 100 = **136.65**
- amount_total = 911.00 + 136.65 = **1047.65**
- h = md5("qr_0034443ae") = `61ec9026…` → mod 10 = **7**
- статус = **DECLINED**, `error_code = CARD_DECLINED`, HTTP 402 — по таблице сценариев (тест T3-2)

Сверка с `payments.csv`: суммы совпадают (911.00 / 136.65), **статус нет** — в seed у p_0003 SUCCESS.
Статусы в `payments.csv` заданы циклом по номеру платежа, а не эмулятором, и совпадают с ним
только в 59 случаях из 100. Поэтому seed считаем историей, а результаты прототипа пишутся
в отдельный `payments_out.csv` (ADR-001, п. 7).

Естественные примеры DECLINED без таблицы сценариев: qr_019, qr_020, qr_037 (h = 8).

## 7. Обработка ошибок

| Ситуация | error_code | HTTP | retryable |
|-|-|-|-|
| QR signature не совпала | INVALID_QR | 422 | нет |
| QR истёк | QR_EXPIRED | 410 | да (новый QR) |
| nonce использован | QR_USED | 409 | нет |
| merchant BLOCKED | MERCHANT_BLOCKED | 403 | нет |
| tip_pct > 50 | TIP_OUT_OF_RANGE | 422 | да (исправить чаевые) |
| amount_total > 2 000 000 | AMOUNT_OUT_OF_RANGE | 422 | нет |
| тот же idempotency_key | — (существующий платёж) | 200 | — |
| эмулятор вернул 8 | CARD_DECLINED | 402 | да (другой способ оплаты) |
| эмулятор вернул 9 | GATEWAY_TIMEOUT | 202, статус PENDING | да (опросить статус) |
| отмена из PENDING | CANCEL_NOT_ALLOWED | 409 | нет |
| отмена из SUCCESS | CANCEL_NOT_ALLOWED | 409 | нет |

Полный каталог (26 ситуаций) — ADR-006.

## 8. Идемпотентность

Клиент генерирует `idempotency_key` (UUID v4) один раз на нажатие «Оплатить» и повторяет его при ретраях.

- **Тот же ключ и то же тело запроса** → HTTP **200**, возвращается **тот же** `payment_id` в текущем статусе.
  Шлюз повторно не вызывается, новая строка не пишется.
- **Тот же ключ, другое тело** (например, другой `tip_pct`) → 409 `IDEMPOTENCY_CONFLICT`.
- **Ключ ищется сразу после проверки подписи**, раньше проверок срока и nonce. Поэтому повтор
  после SUCCESS или после истечения QR тоже получает 200 и свой платёж, а не `QR_USED` или `QR_EXPIRED`.
- **Строки в CSV:** `payments.csv` — seed, не меняется (100 строк, контроль `md5sum`).
  В `payments_out.csv` на один ключ приходится **ровно одна** строка, сколько бы раз запрос ни повторили.
- Запись ключа и платежа атомарна (уникальный индекс `(qr_id, idempotency_key)`),
  иначе два параллельных запроса создали бы два платежа.

## 9. Аудит

Поля события (9, сверх требуемых 8):

1. `event_id` — `evt_NNNN`
2. `payment_id` — привязка к платежу
3. `qr_id` — все попытки по одному чеку
4. `action` — payment_created / payment_submitted / payment_confirmed / payment_declined / payment_canceled
5. `from_status` — статус до перехода (null при создании)
6. `to_status` — статус после перехода
7. `amount_total` — сумма на момент события
8. `actor` — client / system / officer
9. `at` — время UTC
