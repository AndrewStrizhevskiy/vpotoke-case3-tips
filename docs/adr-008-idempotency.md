# ADR-008. Идемпотентность создания платежа

Статус: черновик (архитектор), 2026-11-02.

## Контекст

P-2 требует при повторе `idempotency_key` вернуть уже созданный платёж с HTTP 200,
а тест T3-4 — «тот же payment_id, одна строка в CSV».
В прототипе идемпотентности нет: `payment_id` строится из номера QR
(`p_demo_{qr_id[-3:]}`), и каждый запуск дописывает новую строку.

## Решение

- `idempotency_key` — UUID v4. Клиент генерирует его **один раз на нажатие «Оплатить»**
  и повторяет при сетевых ретраях.
- Ключ уникален в пределах `qr_id` и хранится 24 часа (не дольше жизни QR).
- Сервер хранит запись (`key`, `qr_id`, `request_hash`, `payment_id`, `created_at`).
  `request_hash` = SHA-256 от канонического тела запроса (`qr_id`, `receipt_id`, `base_amount`,
  `tip_pct` или `tip_amount`).

| Ситуация | Ответ |
|-|-|
| Новый ключ | 201, создан платёж CREATED |
| Тот же ключ, тот же `request_hash` | 200, **тот же** платёж в его текущем статусе, новой строки нет |
| Тот же ключ, другой `request_hash` | 409 `IDEMPOTENCY_CONFLICT` |
| Другой ключ, по QR уже есть CREATED или PENDING | 409 `PAYMENT_IN_PROGRESS` (ADR-002) |

- Запись ключа и создание платежа выполняются **атомарно** (одна транзакция,
  уникальный индекс по `(qr_id, idempotency_key)`). Иначе два параллельных запроса создадут два платежа.
- `confirm` идемпотентен по статусу: повторный confirm для PENDING или финального платежа
  возвращает текущий статус и не вызывает шлюз повторно.

### Прототип

- Перед записью прототип ищет ключ в `payments_out.csv` (колонка `idempotency_key`, ADR-005).
- `payment_id` выдаётся последовательно: следующий свободный `p_NNNN` после seed
  (то есть с `p_0101`), а не из номера QR.

## Последствия

- Тест T3-4: два запуска с одним ключом дают одинаковый `payment_id`, `wc -l payments_out.csv`
  увеличивается на 1, второй ответ — HTTP 200.
- Двойное списание (угроза U-4) закрывают вместе: ключ, блокировка QR и погашение nonce.
