# Руководство аналитика

Твои файлы: `02_правила.md`, `02_roles.md`, `03_data_dictionary.md`, `04_requirements.md`, `09_reports.md`.
Шаблоны лежат в `case/`. Копируй шаблон в `docs/` под английским именем
(`docs/02-rules.md`, `docs/02-roles.md`, `docs/03-data-dictionary.md`, `docs/04-requirements.md`,
`docs/09-reports.md`) и заполняй копию. Оригинал в `case/` не трогай.

Решения уже приняты в ADR, твоя задача — оформить их в шаблонах и **сверить с данными**.
Если не согласен с решением, пиши архитектору, а не меняй молча: на ADR ссылаются схемы, API и тесты.

## 1. `02_правила.md` — проверки QR и правила платежа

- Q-3…Q-6 и P-2…P-4 бери из подсказок шаблона, коды — из [B.2](../b2-error-matrix.md).
- Добавь колонку **«Обоснование»**: этого требует раздел B.1 приложения.
- Порядок выполнения не совпадает с нумерацией: Q-6 проверяется вместе с правилами P
  ([ADR-004](../adr-004-validation-order.md)). Сохрани номера, но порядок покажи отдельно.
- Ловушка: P-3 (итог > 2 000 000) при нынешних лимитах недостижим (максимум 1 500 000).
  Обоснование — защита в глубину, см. ADR-004.

## 2. `02_roles.md` — роли и регистрация

- Матрица прав **должна совпасть** с разделом 3 [11-security.md](../11-security.md). Если меняешь там, меняй и здесь.
- Регистрация мерчанта, 4 шага с проверками (подсказка: мерчант не может активировать себя сам):
  заявка мерчанта → система проверяет формат и уникальность, статус PENDING →
  администратор проверяет и активирует (PENDING → ACTIVE) → система выдаёт доступ и пишет событие в аудит.
- Регистрация сотрудника, 3–4 шага: мерчант приглашает → сотрудник принимает приглашение →
  реквизиты вводит у провайдера выплат, платформа сохраняет только маску `****NNNN` и токен →
  сотрудник активен и может выпускать QR на себя.
- Не забудь пункт приёмки: клиент сканирует только QR своего чека (QR привязан к `receipt_id`, ADR-003).

## 3. `03_data_dictionary.md`

- Сущности и ограничения бери из [A.2](../a2-er-model.md). Это заполненный ER-шаблон.
- **Примеры — только из реальных CSV** (`prototype/01_данные/`), например `e_001`, `****1001`,
  `qr_001`, `c82561`, `68d0f361ac38c12b`.
- Колонка «Код ошибки» — коды из B.2 (в шаблоне ссылка на `08_errors.md` ошибочна: там ER-модель).
- В `payments.csv` 7 колонок. Четыре новые (`qr_id`, `idempotency_key`, `amount_total`, `error_code`)
  есть только в `payments_out.csv` прототипа — опиши их отдельной таблицей.

## 4. `04_requirements.md`

- FR-1…FR-10 должны покрыть: генерацию QR, проверку подписи и срока, форму чаевых (с «своей суммой»),
  создание платежа с идемпотентностью, подтверждение через эмулятор, отмену, отчёты (3 разреза),
  регистрацию мерчанта, регистрацию сотрудника. Аудит — FR или NFR, на твой выбор.
- NFR, обязательные по подсказке: TTL QR, HMAC, маскирование `payment_details`, аудит.
  Из ADR-009 добавь rate limit, время в UTC, секреты вне Git.
- В колонке «Тест» ссылайся на T3-1…T3-9. Шаблон ссылается на `10_tests.md`, такого файла нет:
  тесты в `03_тесты.md` и в [B.2](../b2-error-matrix.md#покрытие-тестами).
- Сценарии пиши от лица клиента **и** официанта. «Отмена» и «отказ» — разные сценарии.

## 5. `09_reports.md`

- Пример из шаблона (550 / 4 / 0.75) **не сходится** с данными. Используй контрольные значения
  из [ADR-007](../adr-007-reporting.md): m_001 → 414.85 / 6 / 9.00 / 0.83, e_001 → 83.60 / 2 / 41.80 / 2025-11-03.
- Чаевые и средние считаются только по SUCCESS, количество платежей — по всем статусам.
- Пересчитай сам (Excel или Python) и запиши в журнал, как проверял.
