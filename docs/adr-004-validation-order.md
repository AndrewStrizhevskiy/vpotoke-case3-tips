# ADR-004. Порядок проверок, лимиты и расчёт сумм

Статус: черновик (архитектор), 2026-11-02.

## Контекст

- Q-6 (`tip_pct > 50`) записан среди проверок QR, хотя проверяет параметр платежа.
- P-3 (`amount_total > 2 000 000`) недостижим: при `base_amount ≤ 1 000 000`
  и `tip_pct ≤ 50` итог не больше 1 500 000. В данных максимум итога — 4 585.05.
- В диалоге есть вариант «своя сумма», а `TipCreate` принимает только `tip_pct`.
- Прототип считает суммы через `round(float)`, и это даёт ошибку в копейку:
  53.50 × 5 % → `round` выдаёт 2.67, правильно 2.68.

## Решение

### Порядок проверок (8 шагов, первая ошибка прерывает обработку)

| Шаг | Что проверяем | Ошибка |
|-|-|-|
| 1. Валидация запроса | формат id по шаблонам `m_NNN`, `qr_NNN`…, типы, обязательные поля | 400 `VALIDATION_ERROR` |
| 2. Проверка QR и повтор | Q-1 подпись → P-2 поиск по `idempotency_key` (найден — ответ сразу, ADR-008) → Q-2 `exp ≥ now` → Q-3 nonce не погашен → Q-4 мерчант ACTIVE → Q-5 `receipt_id` совпадает | 422 / 200 или 409 / 410 / 409 / 403 / 422 |
| 3. Расчёт суммы | сверка с реестром (ADR-003) → P-1 диапазон чека → Q-6 диапазон чаевых → P-3 итог | 422 |
| 4. Создание | блокировка QR (ADR-002) → CREATED, атомарно с записью ключа (ADR-008) | 409 `PAYMENT_IN_PROGRESS` |
| 5. Подтверждение | CREATED → PENDING, вызов эмулятора; повторный confirm — по ADR-002 | 409 `PAYMENT_STATE_CONFLICT` (confirm для CANCELED) |
| 6. Результат | SUCCESS / DECLINED / PENDING по ADR-001 | 402 / 202 |
| 7. Отмена | только из CREATED (P-4); повторная отмена CANCELED → 200 | 409 `CANCEL_NOT_ALLOWED` |
| 8. Аудит | событие на каждый переход, запись вместе с переходом | — |

Почему подпись проверяется первой: пока QR не подтверждён, остальным его полям доверять нельзя.
Если сначала проверить `exp`, неподписанный QR получит 410 вместо 422, и атакующий
узнает о системе больше, чем нужно.

Почему повтор (P-2) проверяется сразу после подписи: повтор относится к уже созданному платежу,
и на него не должны влиять проверки, которые после создания изменились. Если сначала проверить
nonce, повтор после SUCCESS получит 409 `QR_USED`; если срок — повтор после `exp` получит 410.
А клиенту нужен его платёж с HTTP 200. До подписи искать нельзя: без неё `qr_id` не подтверждён.
(Изменено 2026-11-02 по ревью PR #1, раньше P-2 стоял на шаге 4.)

Нумерация Q-6 сохранена ради трассировки к материалам кейса,
но выполняется это правило на шаге 3, вместе с правилами P.

### Лимиты

| Правило | Условие | Код |
|-|-|-|
| P-1 | `0 < base_amount ≤ 1 000 000` | `AMOUNT_OUT_OF_RANGE` |
| Q-6 | `0 ≤ tip_pct ≤ 50` или `0 ≤ tip_amount ≤ base_amount × 0.5` | `TIP_OUT_OF_RANGE` |
| P-3 | `amount_total ≤ 2 000 000` | `AMOUNT_OUT_OF_RANGE` |

P-3 оставляем как инвариант (защита в глубину): он сработает, если поменяют лимиты P-1 и Q-6,
а при нынешних лимитах достижим только при ошибке в коде.

### «Своя сумма»

`TipCreate` принимает **ровно одно** из полей `tip_pct` (целое 0..50) или `tip_amount`.
Если пришли оба или ни одного — 400 `VALIDATION_ERROR`.

### Расчёт

```
tip_amount   = round_half_up(base_amount × tip_pct / 100, 2)   # или tip_amount из запроса
amount_total = base_amount + tip_amount
```

Деньги считаются в `Decimal` (или в копейках, целым числом), округление — `ROUND_HALF_UP`.
Float для денег запрещён. Проверка на данных: 637.00 × 5 % = 31.85, итог 668.85 (T3-1);
911.00 × 15 % = 136.65, итог 1 047.65 (T3-2). Обе суммы совпадают с `payments.csv`.

## Последствия

- В схему `TipCreate` добавляется `tip_amount` (`oneOf` с `tip_pct`).
- В прототипе `calc_amounts()` переписывается на `Decimal`.
- Таблица правил в приложении (B.1) строится по этому порядку проверок, а не по номерам.
