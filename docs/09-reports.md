# Отчётность — кейс 3

Заполненная копия [шаблона](../case/09_reports.md), согласована с [ADR-007](adr-007-reporting.md) и схемами Report, EmployeeReport, DailyReport в [OpenAPI](../api/05_api_schemas.yaml). Числа 550 / 4 / 0.75 из шаблона заменены результатами независимого пересчёта исходного `payments.csv`.

## Общие правила

Источник истины — Payment, не ранее сохранённый Report. Сначала фильтруем владельца и период, затем агрегируем. Исторические платежи учитываются по своему статусу, независимо от нынешнего статуса мерчанта и истёкшего QR. В seed 100 попыток: 70 SUCCESS, по 10 DECLINED, PENDING и CANCELED. Они не обязаны воспроизводить результаты эмулятора.

Даты `from` и `to` включительны в UTC: от 00:00:00 from до 00:00:00 следующего дня после to, правая граница исключена. `period = 2025-11` в примерах означает полный ноябрь 2025. Другие интервалы фильтруются по тем же границам; формат поля period для немесячного интервала архитектурой/API ещё не определён и требует согласования. `from > to` и неверные даты отклоняются как VALIDATION_ERROR (400).

Для выбранного множества попыток P: S — только платежи со status = SUCCESS. Деньги и средние считаем в Decimal, округляем **только конечный результат** до 0.01, ROUND_HALF_UP. Долю успехов возвращаем числом 0–1; avg_tip_pct — в процентах 0–50, а не долей и не взвешенным процентом.

| Метрика | Формула | Статусы |
|---|---|---|
| payments_count | count(P) | Все попытки |
| success_count (внутренняя) | count(S) | SUCCESS |
| tips_total | sum(S.tip) | SUCCESS |
| avg_tip_pct | sum(S.tip / S.amount × 100) / count(S) | SUCCESS |
| avg_tip_amount | tips_total до округления / count(S) | SUCCESS |
| success_rate | count(S) / count(P) | Все попытки в знаменателе |
| top_day | UTC-день с максимальной суммой успешных чаевых | SUCCESS |

Для пустого результата tips_total = 0.00, payments_count = 0, avg_tip_pct/avg_tip_amount/top_day = null. При отсутствии успешных попыток средние и top_day также null, success_rate = 0.00 при ненулевом числе попыток. Для полностью пустого P принимается success_rate = 0.00 (схема Report не допускает null); это явное дополнение аналитика для согласования. Дни без попыток не включаем в daily, пустой интервал возвращает `daily: []`. При равных суммах top_day предлагаем выбирать самый ранний день UTC. Политики нулевого знаменателя, равенства top_day и отсутствующих дней ADR-007 не задаёт: до реализации подтвердить их у архитектора; приведённые seed-примеры от этого выбора не зависят.

## 1. Отчёт мерчанта

`GET /api/v1/reports/tips?merchant_id=m_001&from=2025-11-01&to=2025-11-30`

| Метрика | Подстановка по CSV | Результат |
|---|---|---|
| tips_total | 245.90 + 168.95 | 414.85 |
| payments_count | Все 6 попыток, из них 5 SUCCESS | 6 |
| avg_tip_pct | Среднее 5 отношений tip/amount × 100 | 9.00 |
| success_rate | 5 / 6 | 0.83 |

```json
{
  "merchant_id": "m_001",
  "period": "2025-11",
  "tips_total": 414.85,
  "payments_count": 6,
  "avg_tip_pct": 9.00,
  "success_rate": 0.83
}
```

Мерчант видит только свой merchant_id из JWT; администратор — все заведения. Чаевые по отклонённой попытке не входят в доход: сумма по всем статусам 611.20 была бы ошибкой.

## 2. Отчёт официанта

`GET /api/v1/reports/tips?employee_id=e_001&from=2025-11-01&to=2025-11-30`

| Метрика | Подстановка по CSV | Результат |
|---|---|---|
| tips_total | p_0001.tip 31.85 + p_0055.tip 51.75, оба SUCCESS | 83.60 |
| payments_count | p_0001 и p_0055 | 2 |
| avg_tip_amount | 83.60 / 2 | 41.80 |
| top_day | 51.75 за 03.11 > 31.85 за 01.11 | 2025-11-03 |

```json
{
  "employee_id": "e_001",
  "period": "2025-11",
  "tips_total": 83.60,
  "payments_count": 2,
  "avg_tip_amount": 41.80,
  "top_day": "2025-11-03"
}
```

Официант получает только свои данные: employee_id из JWT, чужой параметр → 403 ACCESS_DENIED. Мерчант может видеть данные только сотрудников своего заведения, администратор — всех (просмотр чаевых по RBAC); официант не получает общий отчёт заведения. У клиента доступа к отчётам нет. Для /reports/tips задаётся ровно один фильтр merchant_id или employee_id, оба/ни одного → 400 VALIDATION_ERROR.

## 3. Отчёт по дням

`GET /api/v1/reports/tips/daily?merchant_id=m_001&from=2025-11-01&to=2025-11-30`

| Поле | Формула | 2025-11-01 | 2025-11-03 |
|---|---|---|---|
| date | UTC-дата timestamp, сортировка по возрастанию | 2025-11-01 | 2025-11-03 |
| tips_total | sum(tip) только SUCCESS этого дня | 245.90 | 168.95 |
| payments_count | Все попытки этого дня | 3 | 3 (одна DECLINED) |
| avg_tip_pct | avg(tip / amount × 100) только SUCCESS этого дня | 10.00 | 7.50 |

```json
{
  "merchant_id": "m_001",
  "daily": [
    {"date": "2025-11-01", "tips_total": 245.90, "payments_count": 3, "avg_tip_pct": 10.00},
    {"date": "2025-11-03", "tips_total": 168.95, "payments_count": 3, "avg_tip_pct": 7.50}
  ]
}
```

Доступ как к отчёту мерчанта. Контроль: сумма дневных tips_total = 414.85, сумма count = 6. Средний процент месяца нельзя получить простым средним дневных средних: (10 + 7.5) / 2 = 8.75 неверно; взвешиваем по **числу SUCCESS**: (10 × 3 + 7.5 × 2) / 5 = 9.00.

## 4. Воспроизводимая проверка

Из корня репозитория:

```bash
python3 docs/checks/analyst_data.py
(cd prototype/01_данные && md5sum -c MD5SUMS)
```

Скрипт использует стандартную библиотеку, CSV только читает. Проверяет число колонок, уникальность ключей, FK, маски, форматы nonce/signature, лимиты сумм, соответствие всех 100 Payment ↔ QR по числовому суффиксу, мерчанту, сотруднику и дню; вычисляет три ответа и сравнивает с контрольными значениями. Внешняя проверка сверяет JSON со схемами OpenAPI. Это проверка аналитических расчётов, не работающего HTTP-сервиса: отчётные endpoint'ы пока представлены спецификацией.
